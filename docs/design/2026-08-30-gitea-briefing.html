Gitea 도입 브리핑 — 다중 프로젝트 forge

2026-08-30 · 설치 전 검토 · 결정 근거: OhMyEnglish/docs/design/2026-08-30-wiki-task-tooling-decision.md (8cf5aea)
용도가 한 프로젝트에서 여러 프로젝트 공통 관리로 확장됨 — 자원·구조를 그 기준으로 다시 계산했다.

한 줄 요약

맥에 단일 네이티브 프로세스 하나를 띄워 이슈 · PR 리뷰 · 칸반을 여러 프로젝트에 공통으로 제공한다. 외부 DB·컨테이너·리눅스 VM은 전부 0이다. 프로젝트가 늘어도 프로세스는 계속 1개다 — 이것이 다중 프로젝트 용도에서 Gitea를 고른 핵심 이유다.

지금 OhMyEnglish는 remote가 아예 없어서 PR 개념이 성립하지 않는다. 로컬 forge를 remote로 붙이면 그 문제가 리포별로 한 번에 해결된다.

기능 요약 — 켤 것과 끌 것

Gitea는 GitHub 유사 기능을 넓게 덮는데, 다 쓰면 리소스 이점이 사라진다. 아래는 이번 용도에 맞춘 취사선택이다. 기본값은 공식 app.example.ini와 소스에서 이 턴에 직접 확인했다.

필요 자원

메모리 — 여유분 대비

Gitea 165MB (2.3%)여유 7,142MB

엄격한 쪽(전체 RAM 24,576MB가 아니라 현재 여유 7,142MB)을 분모로 잡았다. 이 165MB는 빈 인스턴스 하한이고, 이슈가 쌓이면 bleve 이슈 인덱서(ISSUE_INDEXER_TYPE = bleve, 기본값) 때문에 오른다.

디스크 — Gitea가 실제로 저장하는 양

Gitea는 bare 리포를 저장하므로 비용은 작업 트리가 아니라 .git 크기다. 예컨대 OhMyEnglish는 전체 670MB지만 .git은 7.3MB다. 아래는 이 턴에 du -sh로 직접 측정한 값이다.

플로우 A — 설치 (1회성)

1
brew install gitea
네이티브 단일 바이너리. 현재 미설치 상태를 이 턴에 확인했다 (command -v gitea → 없음).
2
비밀값 3개 생성
gitea generate secret SECRET_KEY · INTERNAL_TOKEN · JWT_SECRET. 조사 때 쓴 값을 재사용하지 않는다 — /tmp/giteatest/에 평문으로 남아 있다.
3
app.ini 작성 — 켤 것/끌 것을 명시
INSTALL_LOCK = true로 설치 위저드를 건너뛴다. 이 최소 구성으로 HTTP 200이 뜨는 것은 조사 단계에서 실제로 확인됐다.
4
기동 → HTTP 200 확인 → 유휴 메모리 재측정
165MB는 조사 시점 값이다. 설치 후 이 맥에서 다시 재보고 그 값을 기록한다.
5
관리자 계정 + Organization 1개 생성
gitea admin user create --admin. org 아래에 프로젝트 리포를 모으면 칸반·권한이 한 곳에서 관리된다.
6
리포를 하나씩 편입 — OhMyEnglish부터
git remote add local http://127.0.0.1:<포트>/<org>/<repo>.git → git push --all. remote가 없는 곳이 가장 이득이 크다.
7
백업 경로 정하기
SQLite와 bare 리포가 한 디렉터리에 모인다. gitea dump 또는 그 디렉터리 자체를 백업 대상에 넣는다 — 이슈·PR·리뷰 코멘트는 리포가 아니라 SQLite에만 있다.

플로우 B — 일상 운영

결정 2번(TASKS.md가 상태의 정본)을 지키는 형태다. Gitea는 태스크 원장을 대체하지 않고 리뷰·버그 경로만 담당한다.

TASKS.md 태스크 선택 (정본)→ 브랜치 · 커밋→ push→ PR 생성→ 리뷰 패스 · 라인 코멘트→ 수정→ merge→ TASKS.md 상태 갱신 (정본)

파란 테두리 두 칸이 정본이 사는 곳이다. 버그는 이 루프 밖에서 Gitea 이슈로 들어와 같은 자리에 합류한다. 두 정본을 만들지 않는 것이 이 배치의 목적이다 — 태스크 상태를 이슈에도 이중 등록하지 않는다.

다중 프로젝트 구조 — 결정이 필요한 3건

  1. AgentDev(stock-agent)를 어떻게 할지. 이미 Synology NAS에 self-hosted git remote가 있다(커밋 1,049개). Gitea로 이전할지 · 둘을 병행할지 · 그대로 둘지를 정해야 한다. 병행은 remote 2개를 수동 동기화하는 비용이 붙는다.
  2. GitHub에 있는 리포(AllMyEnglish, ai-driven-development)의 정본을 어디로 둘지. GitHub를 정본으로 두고 Gitea를 push mirror로 쓰는 방향과, Gitea를 정본으로 두고 GitHub로 밀어내는 방향이 갈린다.
  3. git이 아닌 3개(En-Coach 74MB · WSEAgent · Research)를 지금 편입할지. git init이 먼저다. Research는 지금 이 문서가 있는 곳인데 버전 관리가 없다.

이 브리핑이 확정하지 않은 것

  • 165MB는 이 맥에서 내가 재측정한 값이 아니다. 조사 세션이 20초 간격 3회로 168,864~169,232KB를 측정했다. 설치 후 재측정이 플로우 A-4에 들어가 있다.
  • 리포 8개 · 이슈가 쌓인 뒤의 메모리를 모른다. 빈 인스턴스 하한만 안다. bleve 이슈 인덱서가 주 증가 요인이고, 예산(유휴 ≤512MB)을 위협하면 ISSUE_INDEXER_TYPE = db로 내리는 선택지가 있다.
  • 백업·복구를 실제로 돌려보지 않았다. 이슈와 리뷰 코멘트가 SQLite에만 있으므로, gitea dump → 복원까지 1회 리허설하지 않으면 "이슈를 잃지 않는다"고 말할 수 없다.
  • 버전 시효. Gitea v1.27.3은 2026-08-29 릴리스로 조사 시점 하루 차다. MIT.
