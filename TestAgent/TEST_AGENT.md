# TestAgent 운영 계약

## 1. 역할

TestAgent는 제품 구현과 독립된 검증자다. 하나의 테스트 run에서 아래 역할을 순서대로 수행한다.

| 역할 | 책임 | 하지 않는 일 |
| --- | --- | --- |
| Test Orchestrator | 범위·AC·실행 표면·격리 자원·판정 기준을 확정하고 run을 시작한다. | 테스트 중 요구사항을 임의 변경하지 않는다. |
| User-role Runner | 사전에 정한 사용자 페르소나와 입력을 실제 제품 경로에 전달한다. | 구현 내부 함수를 직접 호출해 사용자 흐름을 우회하지 않는다. |
| Evidence Verifier | API 응답, DB 행, 파일, queue, UI 상태처럼 직접 관찰 가능한 산출물을 검사한다. | runner/구현 에이전트의 “성공했다”는 서술만으로 통과시키지 않는다. |
| Reporter | 명령, 관측값, 판정, 잔여 위험, cleanup 결과를 기록한다. | 비밀값·개인정보·운영 접속 문자열을 보고서에 남기지 않는다. |

작은 결정론적 테스트에서는 한 프로세스가 네 역할을 모두 수행해도 된다. 대화형 agent runner를
쓰는 경우에는 Orchestrator와 Runner를 반드시 별도 터미널 또는 세션으로 분리한다.

## 2. 도구·에이전트 중립 계약

TestAgent는 Codex와 Claude를 포함한 특정 코딩 에이전트, CLI, 지침 파일명에 종속되지 않는다.
대상 프로젝트가 어떤 에이전트 환경을 쓰든 아래 네 가지를 제공하는 실행 어댑터로 연결한다.

| 공통 계약 | 의미 |
| --- | --- |
| 입력 채널 | Orchestrator가 runner 또는 제품에 사용자 역할 입력을 전달하는 방법 |
| runner 식별자 | 특정 run의 terminal, session, process, job을 다시 찾는 안정된 식별자 |
| 출력 수집 | runner의 상태·오류·테스트 artifact를 읽는 방법 |
| 완료 신호 | 종료 코드, 명시적 이벤트, artifact 생성, 직접 산출물 검증 중 완료를 판정하는 근거 |

프로젝트의 에이전트 지침 파일명이나 실행 도구는 이 계약의 구현 세부 사항이다. TestAgent 문서에는
특정 도구의 고유 절차를 공통 절차처럼 기록하지 않으며, 도구별 차이는 실행 표면 어댑터에만 둔다.

## 3. 비협상 원칙

1. **AC가 먼저다.** 모든 시나리오는 하나 이상의 Acceptance Criteria에 연결한다.
2. **사용자 경로를 우회하지 않는다.** 가능하면 실제 UI·API·명령 경로로 입력한다.
3. **직접 산출물을 검증한다.** 입력 성공, 로그 한 줄, agent의 서술은 충분한 증거가 아니다.
4. **격리한다.** 테스트 DB·계정·파일·queue는 운영 자원과 분리한다. 파괴적 작업 전 대상과 scope를 읽기 전용으로 확인한다.
5. **결정론을 우선한다.** 시간·외부 LLM·네트워크 등 가변 요소는 fake/stub/고정 fixture로 통제한다. 실제 외부 호출이 목적이면 비용·재시도·cleanup 경계를 별도 시나리오로 둔다.
6. **실패도 산출물이다.** 실패 시 첫 오류 위치, 실제 응답/상태, 재현 명령, 잔여 데이터 여부를 남긴다.
7. **정리까지 검증한다.** 테스트 사용자·임시 파일·세션·예약된 job이 의도대로 정리됐는지 확인한다.
8. **표면은 교체 가능하다.** Orca, 일반 셸, tmux는 runner 전달 방식일 뿐 테스트 계약을 바꾸지 않는다.

## 4. 표준 실행 흐름

```text
AC/위험 경계 확정
  → 사용자 역할 시나리오와 직접 검증 정의
  → 격리 자원·비밀 주입·cleanup 방법 preflight
  → 독립 runner 실행
  → 제품 경로에 사용자 입력 전달
  → API/DB/UI/파일 산출물 직접 검증
  → PASS / FAIL / BLOCKED / ERROR 판정
  → cleanup 검증과 보고서 기록
```

### 판정값

| 판정 | 뜻 | 다음 행동 |
| --- | --- | --- |
| PASS | 모든 기대 산출물과 cleanup이 확인됐다. | 결과를 기록하고 다음 시나리오로 진행 |
| FAIL | 제품 동작이 AC 또는 기대 결과와 다르다. | 재현 증거를 대상 앱의 bug/task에 연결 |
| BLOCKED | 사람의 결정, 권한, 준비되지 않은 외부 자원 등 제품 외 선행 조건이 없다. | 필요한 결정/의존성을 명시하고 `Awaiting Decision` 또는 dependency로 관리 |
| ERROR | runner·테스트 자원·도구 자체가 실패해 제품 판정이 불가능하다. | 환경 오류를 먼저 분리·수정하고 같은 시나리오를 재실행 |

## 5. 사용자 역할 시나리오 작성법

시나리오는 “사용자가 무엇을 했고 시스템이 무엇을 남겨야 하는가”로 쓴다. 구현 함수명이나 내부
테이블 이름만으로 시나리오를 정의하지 않는다.

각 행에는 반드시 다음을 둔다.

- 사용자 페르소나와 시작 상태
- 실제로 전달할 입력 또는 조작
- 저장/외부 호출/권한의 예상 여부
- 사용자에게 보여야 할 결과
- 직접 확인할 산출물
- 실패 시 복구 또는 재시도 기대

정상 흐름 외에 아래 경계를 최소 한 번씩 포함한다.

- 이전 상태 없음, 중복 입력, 취소/수정/삭제
- 권한 없음·잘못된 인증·민감정보
- 로컬 저장·DB·네트워크·비동기 Worker 실패
- 재시도·멱등성·cleanup

## 6. 실행 표면 어댑터

### A. 일반 셸

결정론적 runner를 현재 셸에서 실행한다. 명령의 종료 코드와 stdout만 보지 말고, runner가 검증한
API/DB 산출물과 cleanup assertions를 함께 확인한다.

- 장점: 가장 단순하고 CI에 그대로 옮기기 쉽다.
- 주의: 현재 사용자 셸의 환경 변수를 테스트 결과로 오해하지 않도록 명시적 테스트 환경을 사용한다.
- 계약 매핑: 입력 채널은 표준 입력/CLI 인자, runner 식별자는 process ID 또는 run ID, 출력 수집은 stdout/stderr와 테스트 artifact, 완료 신호는 종료 코드와 직접 산출물이다.

### B. Orca 터미널

Orca가 관리하는 대상 workspace에 새 터미널을 만들고 runner를 실행한다. 대화형 runner의 경우
Orchestrator는 terminal handle을 보관하고, Runner의 질문에는 **사전에 정한 사용자 역할**로만
응답한다.

- terminal title이 아니라 handle을 식별자로 사용한다.
- 입력 전에는 현재 terminal 상태를 읽고, handle stale이면 목록에서 새 handle을 얻는다.
- 대화형 runner는 종료 대기만으로 완료를 판단하지 않는다. 명시적인 완료 신호 또는 직접 산출물 검증을 사용한다.
- 테스트가 끝난 terminal은 대상 앱 정책에 맞춰 닫거나 재사용 목적을 명확히 표시한다.
- 계약 매핑: 입력 채널은 terminal send, runner 식별자는 terminal handle, 출력 수집은 terminal read, 완료 신호는 종료·상태 이벤트·직접 산출물 중 계획에 정한 방식이다.

### C. 새 tmux 세션

새 run마다 고유한 detached tmux 세션을 만든다. Runner 입력은 해당 pane에만 주입하고, 결과는
`capture-pane` 또는 테스트 artifact로 수집한다.

- 기존 사용자 tmux 세션을 재사용하거나 수정하지 않는다.
- 세션 이름은 `<app>-testagent-<run-id>`처럼 대상과 run을 구분한다.
- 성공·실패와 관계없이 capture 후 테스트 세션을 종료한다.
- 장시간 실행은 timeout·heartbeat·중단 방법을 계획에 명시한다.
- 계약 매핑: 입력 채널은 해당 pane, runner 식별자는 session/window/pane, 출력 수집은 pane capture 또는 artifact, 완료 신호는 종료 코드와 직접 산출물이다.

### D. 코딩 에이전트 subagent

구현 세션이 같은 도구 안에서 별도 subagent 프로세스를 띄워 검증자로 쓴다. 프로세스가 분리되므로
작성자와 검증자의 컨텍스트 격리는 성립한다. 다른 세 표면과 달리 **종료 코드가 없고 출력이 자동으로
돌아오지 않는다** — 이 두 가지가 이 표면의 고유 위험이다.

- subagent의 일반 출력은 요청자에게 전달되지 않을 수 있다. 요청 프롬프트에 **보고를 요청자에게
  전송하는 호출을 명시**하고, 그 전송이 실제로 도착한 것만 출력 수집으로 인정한다. 명시하지 않으면
  run이 끝나도 증거가 유실된다.
- **대기 상태 알림을 완료로 읽지 않는다.** "유휴"·"available" 류의 신호는 지금 할 일이 없다는
  뜻이지 시나리오가 끝났다는 뜻이 아니다. §2의 완료 신호는 보고 도착 또는 직접 산출물이다.
- 완료 판정은 보고에 담긴 관측값과 **요청자가 직접 재현한 증거**로 한다. 보고 서술만으로 통과시키지
  않는다(§3 원칙 3). 최소 한 건은 요청자가 같은 명령을 돌려 대조한다.
- subagent 프로세스 자체는 일회성이라 별도 정리 대상이 아니다. subagent가 만든 tmux 세션·임시
  경로에는 §7을 그대로 적용하고, 정리 여부를 보고 항목으로 요구한다.
- 쓰기 도구를 제거한 subagent라도 셸이 있으면 리다이렉션으로 파일을 바꿀 수 있다. 대상 소스
  무수정은 규약으로 지키고, run 전후 저장소 상태로 확인한다.
- 계약 매핑: 입력 채널은 subagent 요청 프롬프트와 후속 메시지, runner 식별자는 subagent 이름,
  출력 수집은 요청자에게 도착한 보고, 완료 신호는 그 보고 도착 또는 직접 산출물이다.

## 7. 테스트 실행 표면 정리

TestAgent가 만든 tmux 세션과 Orca 테스트 터미널은 기본적으로 **일회성 자원**이다. 결과 증거를
수집한 즉시 정리해, 다음 run에 이전 세션·출력이 섞이거나 테스트 프로세스가 계속 남지 않게 한다.

| 표면 | 생성 시 기록할 식별자 | 증거 수집 뒤 정리 | 정리 확인 |
| --- | --- | --- | --- |
| tmux | session/window/pane와 run ID | 정확히 그 테스트 session만 종료 | 세션 목록에서 run ID가 사라졌는지 확인 |
| Orca | terminal handle과 workspace | 정확히 그 handle의 테스트 terminal만 닫기 | workspace terminal 목록에서 handle이 없는지 확인 |
| 일반 셸 | process/run ID, 임시 경로 | 자식 process와 임시 artifact 정리 | 종료 코드와 임시 경로·process 잔존 여부 확인 |
| 코딩 에이전트 subagent | subagent 이름과 그가 만든 tmux 세션·임시 경로 | 프로세스 자체는 정리 대상이 아니다 — 만든 자원만 위 규칙대로 정리 | 보고의 정리 항목과 실제 잔존 여부를 대조 |

- 생성 전에 대상 이름·handle이 기존 사용자 세션인지 확인한다. TestAgent가 만들지 않은 세션,
  pane, terminal, workspace 등록은 종료·삭제하지 않는다.
- tmux는 `<app>-testagent-<run-id>`처럼 명확한 이름을 사용하고, `kill-session`은 그 정확한
  이름에만 적용한다. 광범위한 glob이나 모든 세션 종료 명령은 금지한다.
- Orca는 테스트 terminal만 닫는다. repository/workspace 등록은 재사용 가능한 실행 맥락이므로
  테스트 종료만을 이유로 제거하지 않는다. terminal이 이미 자동 종료되어 handle을 찾지 못하면,
  목록에서 잔존하지 않음을 확인한 뒤 정리 완료로 기록한다.
- 실패·timeout·중단 경로도 동일한 정리를 보장해야 한다. runner는 가능한 경우 cleanup trap 또는
  finally 블록을 사용하고, 정리에 실패하면 결과를 PASS로 판정하지 않는다.
- 사용자가 장기 실행이나 디버깅을 명시적으로 요청한 경우에만 세션을 유지할 수 있다. 이때는
  소유자, 유지 목적, 종료 조건을 결과 보고서에 남긴다.

## 8. 안전 경계

- 운영 DB, 운영 queue, 실제 고객 계정, 실비가 발생하는 외부 호출은 기본 금지다.
- 테스트 DB 이름·테스트 계정·임시 경로의 안전한 식별 규칙을 runner 시작 시 검증한다.
- 토큰·비밀번호·개인 데이터는 명령 출력, terminal capture, 보고서, 스크린샷에서 마스킹한다.
- 실제 외부 호출을 검증해야 하면 비용 상한, 호출 횟수, 승인자, 정산·cleanup 방법을 사전에 문서화한다.
- 실패 주입은 제품의 복구 경계를 확인하기 위한 것이며, 공유 운영 환경 장애를 만들 권한을 뜻하지 않는다.

## 9. 지속 사용 규칙

- 대상 앱의 에이전트 지침 또는 테스트 운영 문서에서 이 파일을 참조한다.
- 앱별 scenario, fixture, runner, 결과는 그 앱 저장소에 둔다.
- 범용 원칙·어댑터·템플릿의 개선만 이 `DevInfra/TestAgent`에 반영한다.
- 새 테스트 표면을 도입하면 기존 표면들과의 차이, 권한 모델, 증거 수집법, cleanup 규칙을 이 문서에 추가한다.
