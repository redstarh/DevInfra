# 4 Lenses 설계/개발/리뷰 프레임워크

> **목적**: 특정 버그가 아니라 버그의 '종류 자체'를 설계 시점에 예방하는 보편적 관점.
> 설계(3~4단계), 개발(5단계), 리뷰(9단계)에서 동일한 4가지 관점을 해상도만 달리하여 적용.

---

## 4가지 관점 (Lenses)

### L1. Contract (계약)

> "이 연산의 전제조건, 사후조건, 불변조건은 무엇인가?"

| 해상도 | 질문 |
|--------|------|
| 설계 | 이 컴포넌트의 public 메서드가 보장하는 것은? 호출자가 보장해야 하는 것은? |
| 개발 | 이 메서드에 None/빈값/음수가 들어오면? 반환 후 상태는 어떤 상태? |
| 리뷰 | 설계서의 계약이 코드에 반영되었는가? 암묵적 가정은 없는가? |

### L2. Boundary (경계)

> "데이터/상태/제어가 어떤 경계를 넘는가?"

경계 유형:
- **시간**: 어제→오늘, 장전→장중→장후, 리셋 전→후
- **프로세스**: 메모리→파일(WAL/DB), 재시작 전→후
- **시스템**: 내부→외부 API, 서비스→서비스
- **타입**: aware→naive datetime, str→int, JSON→객체

| 해상도 | 질문 |
|--------|------|
| 설계 | 경계를 넘는 데이터는 무엇인가? 넘을 때 변환/검증이 필요한가? |
| 개발 | 외부 데이터 파싱에 방어 코드가 있는가? 영속 데이터의 유효기간은? |
| 리뷰 | 경계를 넘는 모든 지점에 변환/검증이 있는가? |

### L3. Failure (실패)

> "실패하면, 부분적으로 실행되면, 중간에 중단되면?"

| 해상도 | 질문 |
|--------|------|
| 설계 | 이 연산이 실패할 수 있는 시나리오는? 실패 시 시스템 상태는? |
| 개발 | 예외 발생 시 상태가 절반만 바뀌는가? 자원을 잡고 있다가 실패하면? |
| 리뷰 | 에러 경로에서 자원 정리가 되는가? 실패 후 재시도가 안전한가? |

### L4. Dependency (의존)

> "무엇이 무엇에 의존하고, 순서가 있는가?"

| 해상도 | 질문 |
|--------|------|
| 설계 | 컴포넌트 간 초기화/정리 순서는? 순환 의존은 없는가? |
| 개발 | 이 값을 읽기 전에 갱신이 보장되는가? 호출 순서 제약이 있는가? |
| 리뷰 | 설계의 순서 제약이 코드에서 지켜지는가? 단독 테스트 가능한가? |

## 적용 규칙

### 트랙별 적용 범위

| 트랙 | 설계서 4L 섹션 | 개발 시 체크 | 리뷰 시 체크 |
|------|:---:|:---:|:---:|
| A (풀) | 필수 — 4개 전부 | 필수 | 필수 |
| B (라이트) | 해당 관점만 | 해당 관점만 | 해당 관점만 |
| C (문서) | 불필요 | 불필요 | 불필요 |
| D (분석) | 불필요 | 불필요 | 불필요 |

- 클래스 불변조건:

### Boundary
- 경계를 넘는 데이터/상태:
- 경계별 변환/검증 방법:

- 실패 시나리오:
- 부분 실행 시 상태 복원 방법:
